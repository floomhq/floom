# Floom Product Spec

## The OS for Background Workers

Floom lets users spawn background workers, give them secrets/tools, run them manually or through triggers, and observe every execution.

The core promise:

> Create a worker. Give it tools. Let it run. See everything.

---

# 1. Product Thesis

Companies will increasingly run work through small autonomous or semi-autonomous workers.

These workers may be:

- AI agents
- Python scripts
- API automations
- research workers
- reporting workers
- CSV processors
- lead enrichment workers
- support triage workers
- browser automation workers

They need an operating layer.

Floom provides that layer:

- creation
- execution
- triggers
- secrets
- sandboxing
- logs
- outputs
- approvals
- observability

Floom is not a visual workflow builder.
Floom is not Zapier.
Floom is not n8n.
Floom is not a prompt playground.

Floom is the OS for background workers.

The entire The initial release should optimize for this loop:

# 3. Product Primitives

## 3.1 Worker

A worker is an executable unit of work. AI-based or non-AI-based. Represented as a folder:

```txt
workers/
  weekly_update/
    worker.yml
    run.py
    requirements.txt
```

## 3.2 Trigger

The initial release supports: Manual, Schedule, Webhook. No other triggers in the initial release.

## 3.3 Run

A run is one execution. Stores: worker id, status, trigger source, input, logs, output, artifacts, errors, timestamps, approval status.

## 3.4 Secret

Private value available to a worker (OPENAI_API_KEY, APOLLO_API_KEY, etc.). For local development, secret values live in `.env`. The database stores metadata only.

## 3.5 Artifact

File/output generated by a worker (markdown report, CSV, JSON, PDF, image, email draft).

## 3.6 Approval

Human checkpoint before a worker completes a sensitive action (send email, post to Slack, update CRM, publish report, write to database).

## 3.7 Log

Logs make runs observable. Human-readable first, technical second.

# 8. Worker Format

## 8.1 Worker Folder

Every worker lives in its own folder with `worker.yml`, `run.py`, `requirements.txt`.

## 8.2 worker.yml example

```yaml
id: weekly_update
name: Weekly Update
description: Turns raw notes into a polished weekly company update.

trigger:
  type: manual

runtime:
  type: python
  entrypoint: run.py
  runner: e2b

inputs:
  - name: notes
    label: Raw notes
    type: textarea
    required: true
    placeholder: Paste notes, bullets, metrics, updates...
  - name: audience
    label: Audience
    type: select
    required: true
    options: [internal, investor, customer]
    default: internal

secrets:
  - OPENAI_API_KEY

outputs:
  - name: update
    label: Weekly update
    type: markdown

approvals:
  required: true
  label: Approve final update
```

## 8.3 Supported Input Types

text, textarea, number, select, file, boolean

## 8.4 Supported Output Types

markdown, text, json, csv, file

## 8.5 Supported Runtime Types

Initial release: python. Later: node, bash, browser.

# 9. Worker Code Contract

Script workers are process entrypoints. The runner executes `exec.command`
from the worker working directory, writes the run payload to `inputs.json`, and
expects the process to write `result.json` in that same working directory before
exiting. Declared secrets are exposed as environment variables. Declared
connection identifiers are exposed through `connections.json`.

`result.json` on success:

```python
{
  "status": "success",
  "outputs": {"key": "value"},
  "artifacts": []
}
```

`result.json` on failure:

```python
{"status": "error", "error": "Missing input: notes"}
```

# 10. Execution Model

## 10.1 E2B Runner

Default for script workers. Use E2B for dependency isolation and user-submitted code.

Worker config:

```yaml
runtime:
  type: python
  entrypoint: run.py
  runner: e2b
```

Do not require E2B for the first version.

---

# 11. Trigger Model

## 11.1 Manual Trigger

Primary V0 trigger. User clicks Run now. UI generates a form from `worker.yml`.

## 11.2 Schedule Trigger (later release)

```yaml
trigger:
  type: schedule
  cron: "0 9 * * MON"
```

Simple scheduler loop in FastAPI. No complex recurrence UI.

## 11.3 Webhook Trigger (later release)

Each worker gets a webhook URL: `POST /webhooks/{worker_id}`. Request body becomes run input.

## 11.4 Pre-defined Inputs (automated triggers)

Schedule/webhook/event triggers have no Run form, so they use the worker's saved
`input_values` defaults. The scheduler injects them and **skips** a fire whose
*required* inputs are unset; webhook/event payloads are **merged** over the
defaults (payload wins). See AUTHORING.md for details.

## 11.5 Worker-to-Worker Calls

A worker may invoke other workers via a top-level `calls:` allowlist in
`worker.yml`. Enforced server-side (and in a signed call token): only allowlisted
worker IDs are callable, chain depth is capped at `MAX_CALL_DEPTH` (3), and a
single run may spawn at most `MAX_WORKER_CALLS_PER_RUN` (50) child runs.

---

# 12. Secrets Model

## 12.1 Local Secrets

Secret values live in `.env`. Database stores only metadata (name, status, last_used_at, workers_using_it).

## 12.2 Secret Resolution

When a worker declares `secrets: [OPENAI_API_KEY]`, the backend checks `.env`. If present: status=available. If not: status=missing.

Never show secret values in the UI.

# 13. Database Schema

Use SQLite for the initial release.

## 13.1 workers

```sql
CREATE TABLE workers (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT,
  config_json TEXT NOT NULL,
  status TEXT DEFAULT 'healthy',
  trigger_type TEXT,
  runner TEXT,
  created_at TEXT,
  updated_at TEXT
);
```

## 13.2 runs

```sql
CREATE TABLE runs (
  id TEXT PRIMARY KEY,
  worker_id TEXT NOT NULL,
  status TEXT NOT NULL,
  trigger_source TEXT NOT NULL,
  runner TEXT NOT NULL,
  input_json TEXT,
  output_json TEXT,
  approval_status TEXT DEFAULT 'not_required',
  error TEXT,
  started_at TEXT,
  completed_at TEXT,
  created_at TEXT,
  FOREIGN KEY(worker_id) REFERENCES workers(id)
);
```

## 13.3 logs

```sql
CREATE TABLE logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id TEXT NOT NULL,
  level TEXT DEFAULT 'info',
  message TEXT NOT NULL,
  timestamp TEXT,
  FOREIGN KEY(run_id) REFERENCES runs(id)
);
```

## 13.4 artifacts

```sql
CREATE TABLE artifacts (
  id TEXT PRIMARY KEY,
  run_id TEXT NOT NULL,
  name TEXT NOT NULL,
  type TEXT,
  path TEXT NOT NULL,
  size_bytes INTEGER,
  created_at TEXT,
  FOREIGN KEY(run_id) REFERENCES runs(id)
);
```

## 13.5 approvals

```sql
CREATE TABLE approvals (
  id TEXT PRIMARY KEY,
  run_id TEXT NOT NULL,
  worker_id TEXT NOT NULL,
  status TEXT NOT NULL,
  label TEXT,
  preview TEXT,
  created_at TEXT,
  decided_at TEXT,
  FOREIGN KEY(run_id) REFERENCES runs(id),
  FOREIGN KEY(worker_id) REFERENCES workers(id)
);
```

## 13.6 secrets

```sql
CREATE TABLE secrets (
  name TEXT PRIMARY KEY,
  status TEXT NOT NULL,
  last_used_at TEXT,
  created_at TEXT,
  updated_at TEXT
);
```

## 13.7 schedules (later release)

```sql
CREATE TABLE schedules (
  id TEXT PRIMARY KEY,
  worker_id TEXT NOT NULL,
  cron TEXT NOT NULL,
  enabled INTEGER DEFAULT 1,
  next_run_at TEXT,
  last_run_at TEXT,
  created_at TEXT,
  updated_at TEXT,
  FOREIGN KEY(worker_id) REFERENCES workers(id)
);
```

# 14. API Spec

Base URL: `http://localhost:8000`

## 14.1 Workers

- `GET /workers` — list all
- `GET /workers/{worker_id}` — one with full config
- `POST /workers/reload` — rediscover from disk

## 14.2 Runs

- `POST /workers/{worker_id}/runs` — create run
- `GET /runs` — list (query: worker_id, status, limit)
- `GET /runs/{run_id}` — detail
- `GET /runs/{run_id}/logs` — logs

## 14.3 Approvals

- `GET /approvals` — pending
- `POST /runs/{run_id}/approve`
- `POST /runs/{run_id}/reject` — body `{reason}`

## 14.4 Secrets

- `GET /secrets` — metadata

# 16. UI Design Direction

Feel: calm, operational, trustworthy, focused, premium, lightweight, not overly technical.

Inspiration: Linear, Notion Calendar, Raycast, Apple internal tools.

Use: warm off-white background, near-black text, subtle gray cards, soft shadows, rounded corners, whitespace, minimal borders, clean typography.

Avoid: dark hacker aesthetic, terminal-heavy UI, enterprise dashboard clutter, colorful chart overload, gradients everywhere, neon, node graphs.

Copy: Worker, Run, Trigger, Secret, Approval, Artifact, Logs. Avoid: magic, AI agent swarm, workflow superpowers, autonomous brain.

---

# 17. Status Model

Worker: healthy, needs_attention, paused, missing_secret, error.

Run: queued, running, completed, failed, pending_approval, approved, rejected.

Approval: not_required, pending, approved, rejected.

---

# 18. Observability Requirements

Initial observability must include: logs, run status, timestamps, duration, input, output, errors, artifacts, approval state.

Do not build: token-level tracing, LLM evals, advanced metrics, distributed tracing, complex cost dashboards.

The UI must answer: What ran? Why did it run? What did it do? What did it produce? Did it fail? Does it need approval?

# 20. Implementation Phases

## Phase 0: 60-90 Minute Prototype

Build: Next.js UI, FastAPI API, SQLite, worker discovery, manual run, logs, output, approvals. Skip: auth, schedule, webhook, E2B, real connection system, secret editing UI.

## Phase 1: Real Local Development

Add: worker scaffold command, `.env` secret detection, artifacts, better error handling, worker reload, run detail page, approval inbox, UI polish.

## Phase 2: Trigger Runtime

Add: schedule trigger, webhook trigger, next_run_at, scheduler loop, webhook endpoints.

## Phase 3: Sandbox Runtime

Add: E2B runner, per-worker runner config, dependency installation, stdout/stderr capture, artifact sync from sandbox.

## Phase 4: Hosted Runtime

Add: auth, Postgres, hosted workers, encrypted secrets, team workspaces, deployment model.

# 25. Final MVP Definition

The initial release is done when:

1. A worker folder can be discovered
2. The worker appears in the UI
3. The UI generates a run form from worker.yml
4. The user can run the worker manually
5. The backend executes run.py
6. Logs are stored and displayed
7. Output is stored and displayed
8. Approval can be required
9. User can approve/reject a run
10. Secret availability is detected from .env

Everything else is optional.
