## NEW DEFECTS

### NEW-P1 — Intermittent worker-run failure under concurrency (`RuntimeError: Event loop is closed`)
- **Severity:** P1 (intermittent, but affects "workers that actually run"; recurs whenever 2+ runs overlap, including scheduler fan-out).
- **Surface:** any worker run; `error_code: agent_runtime_error`, `error: "Event loop is closed"`, `retryable: true`.
- **Repro:** trigger 4+ worker runs within a few seconds (e.g. concurrent `POST /workers/<id>/runs`). A subset fail; the same workers pass when run solo. Confirmed: `research_brief` failed 3× under concurrency (run_8d68be9cf193, run_bd593adb5874, etc.) but PASSES solo (run_1b58ad651768 completed, run_12f326066d87 completed earlier). `github-digest` failed under concurrency (run_f9bf34ca65ee) but passes solo (run_b52b4057d80a completed).
- **Frequency:** 7 occurrences today (06:55–10:26 UTC) in `journalctl -u workeros-api` — predates this audit, recurs naturally.
- **Root cause (confirmed in code + traceback):** `apps/api/runner_sandbox/agent_driver.py` `_run_coro_sync` runs each agent coroutine in its OWN thread via `asyncio.run(coro)` (a fresh event loop per run). The OpenAI Agents SDK / `AsyncOpenAI` httpx streaming client is bound to whichever event loop first created it. When one run's `asyncio.run()` completes it **closes its loop**, and a concurrent run's in-flight streaming response (`openai/_streaming.py aiter_bytes` → `agents/models/openai_responses.py stream_response`) references the now-closed loop → `RuntimeError: Event loop is closed`. Classic "shared async client across multiple event loops" bug.
  - Traceback inner frames: `agent_driver.py:206 _run_agent_async` → `:357 _run_agent_inner` → `:453 _consume_streamed_result` → `agents/result.py:779 stream_events` → `agents/models/openai_responses.py:247 __anext__` → `openai/_streaming.py:319 aiter_bytes`.
- **Operator-visible impact:** the run shows `failed` with the raw string "Event loop is closed" (History tab, /runs list, run-detail Error box) — see shots 05/06/07. The error string is not humanized (an operator won't understand "Event loop is closed"), and a burst of these inflates the "Needs attention" / failed-today counts.
- **Fix direction (for the dispatched fix agent, NOT applied here):** use a single long-lived event loop for all agent runs (`asyncio.run_coroutine_threadsafe` against a persistent loop thread), OR create a fresh `AsyncOpenAI` client bound to the per-run loop inside `_run_agent_inner` (don't share a module-level client across `asyncio.run()` invocations). Additionally humanize the operator-facing error string.

No other NEW P0/P1 found. The prior NEW-P2-A (contexts cold-render blank) did NOT reproduce — file direct-load rendered full content on first cold nav (core flow 4 PASS).
