## Codex adversarial review comment — 2026-06-07 06:25 CEST

### Verdict

The path is directionally right, but the plan is too optimistic unless the gates become live-evidence gates and the issue board is reconciled first. `gh issue list --state open --limit 100` currently returns 46 open issues, not 52, with P0=5, P1=30, P2=1. The largest inconsistency is FL2: GitHub currently labels git-backed workspace storage as P0 (#498), while this plan parks Vivek's git-backed work in the optional parallel lane. A verified-95 plan cannot treat an open P0 as optional; either reclassify #498 with a written launch-scope decision or move it into Wave 2.

### Direct answers to the 6 questions

1. **Sequencing:** Mostly right, with three changes. Keep Wave 1 as deploy-lag clearance. Split Wave 2 into `2A: auth/visibility/isolation` and `2B: run reliability`. Move security P1s (#527 CRLF, #529 share-link leak, #528 setup gate) ahead of UI polish, still after P0s. Keep rename (#519), chat-driven creation (#520), and naming (#512) out of the 95 gate unless Federico explicitly redefines 95 as product-direction completion.
2. **Exit gates:** Not sufficient yet. "All P1 closed+verified-live" is measurable, but "run success >80%" lacks numerator, denominator, time window, and worker cohort. Add exact gates: deployed SHA per surface, live URL, issue number, test command, screenshot/log artifact, run IDs, and a `gh issue list` proof showing zero open P0/P1 or explicit relabel decisions.
3. **Biggest risk:** The biggest verified risk is run reliability (#526), because a 95 score collapses if workers still fail at high frequency after UI/security fixes. De-risk first by querying the last 7 days by runner/worker/error class, isolating `e2b_sandbox_error` vs prompt/tool/config failures, and proving a fixed stock-worker cohort with fresh live run IDs before polishing UI.
4. **Multi-member vs FL1 ordering:** There is a real ordering hazard. FL1 maps local session username `federico` back to legacy owner `federico` for worker routes only (`_worker_access_user_id`), while multi-member/auth routes use UUID session users and `workspace_members`. Deploy FL1 first, then deploy multi-member. Gate the combined deploy with a matrix: secret auth, Federico session auth, admin UUID session, member UUID session, private worker invisibility, workspace-shared worker visibility, run permission, PAT access, scheduler/webhook owner lookup. Do not deploy multi-member over a live DB before confirming `workspace_members(local-default, federico, owner, active)` exists and FL1 still lists the 99 Federico private workers.
5. **Timeline:** If #492/#493/#532 and the Cloud magic-link fix land cleanly today, and #526 has one dominant root cause, verified-95 is realistically 4-6 calendar days. If #498 remains P0 and requires real git-backed storage, use 6-9 days. The current 1-2d + 2-4d estimate omits CI failure cleanup, Cloud repo verification, live deploy propagation, and re-audit churn.
6. **Missing:** Yes. Missing items: reconcile #498 P0 status, explicitly track Cloud magic-link PR/repo because `#113` in this repo is not that PR, verify Cloud engine sync and Cloud dependency installability from `docs/AUDIT_ROUNDS_11_22_TRIAGE_2026-06-05.md`, add prod cross-user/foreign-object probes, add scheduler/webhook owner-lookup probes after multi-member, and add issue-board hygiene as a gate.
