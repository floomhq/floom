# Cloud product audit — 2026-06-23

## Library empty despite existing workers

**Report:** "Library should never be empty if there are workers, since we have memory for each worker?"

**Severity:** P1 (product logic / data durability)  
**Status:** Fixed in cloud overlay (see below). Engine follow-up filed for naming drift.

### How Library is supposed to work

Library (`/app/library`) is the UI for **brain packs** (engine name: contexts). It is **not** a direct view of worker files or `skill_versions._files`.

| Concept | What it is | Where it lives |
| --- | --- | --- |
| **Library folder** | Reusable pack of files workers mount before acting | `CONTEXTS_DIR/{workspace_id}/{name}/` on disk; Supabase Storage bucket `contexts` in cloud |
| **Worker memory pack** | Per-worker writeable folder (default on) | Auto-created as `memory-{worker_id}` with `MEMORY.md`; category `memory`, `sensitive=true` |
| **Worker files** | Manifest, run.py, SKILL.md | Supabase `skill_versions.manifest_json._files` — **not** listed in Library |
| **Run outputs** | Artifacts from executions | Run history — **not** Library |

Data flow:

1. UI `BrainCollection` → `GET /contexts` → `list_contexts()` iterates `current_contexts_root()` directories.
2. Worker create / first run → `ensure_memory_context_pack()` creates `memory-{id}/MEMORY.md` and metadata.
3. Cloud: `startup.py` patches `current_contexts_root()` to stub dirs from Supabase Storage + `.workeros-contexts.json` so listing survives container restarts.

Per-worker memory is **enabled by default** (`WorkerMemoryConfig.enabled = True`). Each worker's config auto-mounts its memory pack (`memory-{worker_id}`).

### Root cause

**Cloud-only durability gap:** Worker memory packs are **sensitive** contexts. They skip git (correct — see `docs/GIT-WORKSPACE-CLOUD.md`). Cloud already uploads sensitive packs to Storage on `_git_commit_context`, but memory packs are created by `ensure_memory_context_pack()` during worker create / first run **without** any git commit or cloud metadata backup.

On Railway's ephemeral filesystem:

1. Worker created → memory pack exists on container disk only.
2. Library may show packs **within the same container session**.
3. Container restart → disk wiped, Storage never had the pack → `_cloud_contexts_root()` finds nothing → **Library empty** while workers still exist in Supabase.

This is **not** an RLS issue, wrong workspace scoping, or UI fetch failure. The API correctly returns `[]` because there are no context directories to enumerate.

### Fix (cloud)

Added `_override_memory_context_persistence_for_cloud()` in `apps/api/startup.py`:

- Wraps `ensure_memory_context_pack` to call `upload_context_background` + `upload_context_metadata` after every materialization.
- Rebinds `e2b_driver` and `agent_capabilities` importers.

Test: `tests/test_cloud_startup_overrides.py::test_cloud_memory_context_pack_uploads_to_storage`

**Existing workspaces:** Memory packs created before this fix were never backed up and cannot be recovered from disk. They reappear after the next worker create, run, or explicit memory materialization (which now uploads to Storage).

### Secondary finding — memory folder naming drift (engine)

| Layer | Convention |
| --- | --- |
| Backend default | `memory-{worker_id}` (`default_worker_memory_context_name`) |
| Workers UI "Connect memory" CTA | `{worker_id}-memory` (`WorkersCollection.tsx`) |

The UI CTA can create/connect a **different** folder name than the backend auto-provisions. Library listing uses backend names; operators clicking "Connect memory" may see a separate folder. **Engine PR required** — [floomhq/workeros-cloud#659](https://github.com/floomhq/workeros-cloud/issues/659).
