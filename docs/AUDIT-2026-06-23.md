### `/app/workers/<id>` Overview — "WHAT IT DOES" flow diagram (A-10)
- **FIXED (UI polish).** The `WorkerAsciiDiagram` central worker node (the box +
  identity glyph) rendered in saturated `--accent` blue while the trigger/input
  and output/result boxes were neutral `--ink`. The lone blue box read as
  off-palette emphasis — the design system reserves the single accent blue for
  interactive/selection states (active nav, links, focus, selection), not a
  static decorative highlight, and bans blue primary emphasis in light mode.
- Root cause: `engine/apps/web/components/WorkerAsciiDiagram.tsx` set the worker
  column cells (`tone: "accent"`) and the worker glyph mark (`tone: "accent"`).
- Fix: both → `tone: "ink"`, matching the input/output nodes. The worker node
  stays the visual focal point structurally (taller 5-row box with name + rule +
  trigger sub-label, plus its centered identity glyph), now without the
  off-palette blue. Connectors remain `--ink-faint`. Synced into `web/` via
  `npm run sync`. Engine submodule bump still required to deploy.

### `/app/connections/redirect` — Composio connect flow (A-11)

- **FIXED (3 root causes), engine-owned** (`engine/apps/web/app/connections/redirect/page.tsx`). Real repro: started connecting Google Calendar → "loaded forever" → clicked a worker → app yanked the user back to the connect screen.
- **(a) Infinite loading.** The completion poll ran for a 2-minute deadline then *silently stopped scheduling without any terminal phase*, so the spinner showed forever. `api.connections.initiate()` also had no timeout, so a hung backend (the related blank `/api/proxy/connections/authorize/<token>` route) left the page stuck on "preparing". Fix: a `timeout` terminal phase ("Still waiting for <provider>" + Check again / Open Composio again / Go to connections) and a 30s `initiate` timeout that surfaces a retryable error.
- **(b) Rogue navigation back to connect screen.** The poll is a recursive `setTimeout`; an in-flight tick resolves *after* the component unmounts (user navigated to a worker). The unmount cleanup only cleared the pending timer, so the stale tick rescheduled a new timer and called `router.replace(returnTo)`, forcibly navigating the user back. Fix: a `cancelledRef` mounted-guard checked at every async boundary; unmount sets it true so stale ticks bail before rescheduling or navigating.
- **(c) Provider name copy bug.** Local `formatProviderName` only title-cased on `-`/`_`, so `googlecalendar` → "Googlecalendar" (and, with stale copy, "Googlecalendaron Composio's page"). Affects all single-token multi-word slugs. Fix: delegate to the shared `getSupportedApp(slug).displayName` map ("Google Calendar", "HubSpot", "GitHub", …). The current explainer copy already has the correct space; the missing-space artifact was a stale deploy.
- Synced into `web/` via `npm run sync`. New DOM tests in `tests/connections-redirect-flow-guard.dom.test.tsx`. ESLint + tsc clean. Engine submodule bump still required to deploy.

### `/app/workers/<id>` Library tab — naming + ~30s load (A-11, A-12)

**Naming (A-11).** The advanced tab read **"Brain"** while the left-nav, `/library`
page, collection title and MCP tool-catalog group all say **"Library"** (the engine
internally calls the feature "brain"/contexts; the operator-facing term was
standardized to "Library"). The lone "Brain" tab was the inconsistency reported.
- Fix: added `WORKER_DETAIL_TAB_LABEL` in `engine/apps/web/lib/workers/tabs.ts`
  mapping the **stable internal id** `Brain` → visible label `Library` (the id,
  route, localStorage pin key and §4 contract test all keep `Brain`).
  `WorkersCollection.tsx` now renders `WORKER_DETAIL_TAB_LABEL[key]`.
- Other user-facing "Brain" strings aligned to "Library": `CommandPalette.tsx`
  nav item, Overview heading "Company brain it uses" → "Library it uses", the
  three Library-tab toasts/errors, `privacy/page.tsx` ("brain folders/files"),
  and the `contexts/page.tsx` secret-warning. Internal context/brain APIs, route
  ids, component names and code comments were left untouched.

**Performance (A-12).** Root cause found: `GET /contexts`
(`engine/apps/api/routers/contexts.py::list_contexts`) builds one row per pack via
`services/context_access.py::_context_summary`, which called `context_dir(name)`
**with hydration enabled**. In hosted mode `context_dir()` runs the cloud hydration
hook (`apps/api/startup.py::_bootstrap_contexts_storage` →
`apps/api/cloud_contexts.py::hydrate_if_missing` → `download_context`), which
**downloads the pack's entire contents from Supabase Storage** — one serialized
`download()` per file plus a recursive `list()` per pack. So merely *listing* the
Library materialized every pack from object storage just to compute file counts =
the ~30s wait.
- Fix (engine, highest-impact): in `_context_summary`, when the cached `summary`
  (already stored in `.workeros-contexts.json`) is present, fetch the path with
  `context_dir(name, hydrate=False)` (the #1813 suppression seam) and use the
  cached metadata — zero Storage downloads. Falls back to the hydrating
  `context_dir(name)` + `context_tree_summary` only when no cached summary exists.
  Regression guard in `engine/apps/api/tests/test_perf_fast_paths.py`.
- Cloud follow-up (#664): the Storage read path itself (`download_context`) is
  still serial per-file when a pack is genuinely opened on a cold container —
  parallelize / cache / single-object manifest. The engine `BrainTab` also fetches
  `api.contexts.list()` with no React Query cache (refetch per tab open).

**Ownership:** tab label = engine; perf list-fix = engine (the fetch);
Storage read latency = cloud. Issues: engine
[floomhq/floom#1945](https://github.com/floomhq/floom/issues/1945), cloud
[#664](https://github.com/floomhq/workeros-cloud/issues/664).

  (`28cb920c…`, 33 assets) matching across hosts; SMOKE PASSED for the right
  reason.
