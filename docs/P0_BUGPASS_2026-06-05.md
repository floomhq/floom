## M73 — Worker Creation Times Out

### Root Cause

The engine already exposes the robust async path:

- Frontend calls `POST /workers/new/from-prompt`.
- API creates a `worker-author` run and returns a `run_id`.
- The UI follows the run over SSE/polling until the generated worker is registered.

The bug was the prompt page fallback. If the async start failed before a run id, the UI fell back to `POST /workers/draft-and-create`. That legacy endpoint performs LLM codegen plus worker smoke/gate work inside the same HTTP request. The frontend proxy binding limit is 60 seconds (`maxDuration = 60` in both the engine proxy and Cloud overlay proxy), and the service uvicorn unit has no shorter request timeout. A slow `gpt-5.5` codegen attempt can exceed the proxy budget and produce `Request timed out. The server took too long to respond.`

The same page also hardcoded `/api/proxy` for EventSource, bypassing Cloud's configured `/app/api/proxy` base path.

### Fix

- Removed the prompt-generation fallback into `draft-and-create`.
- Kept the prompt path async-only after `newFromPrompt`.
- Added a shared `apiProxyPath()` helper.
- Routed worker-author SSE and run stream SSE through the configured proxy base.
- Included `workspace_id` in SSE query strings because EventSource cannot send custom headers.

- `npm run build` in `apps/web`: production build and TypeScript completed successfully.

## M74 — Worker Detail Infinite Loop

### Root Cause

Unauthenticated route checks did not show a Vercel routing loop:

- `curl -I https://workeros.floom.dev/app/workers/granola-hubspot-meeting-actions` returned a login redirect.
- `curl -I https://workers.floom.dev/workers/granola-hubspot-meeting-actions` returned a login redirect.

The reported Cloud URL uses a slug-shaped exact worker id. Cloud Supabase has that worker:

- `id`: `granola-hubspot-meeting-actions`
- `workspace_id`: `ws_b79e570aad8349`
- workspace name: `fede-production`

Federico also has an older/default workspace, `ws_aac663b43cb542`. Cloud `workers.get()` scoped exact id detail lookups to the active workspace cookie. With the stale/default cookie, the exact slug deep link missed the owned row and returned `Worker not found`.

### Fix

Cloud-only repository fix:

- `SupabaseWorkerRepository.get()` still tries the active workspace first.
- On a miss with an active workspace context, it retries by exact worker id plus owner `user_id`.
- The fallback does not expose other users' workers and does not change workspace-scoped list queries.

### Evidence

- `python3 -m pytest tests/test_supabase_repos.py -q` in the Cloud worktree: `4 passed`.
- Patched local Cloud repository probe with active workspace forced to `ws_aac663b43cb542` returned `worker_found=True` for `granola-hubspot-meeting-actions`.

Live verification will be appended after merge/deploy.

## M75 — Run Detail Says Run Not Found

### Root Cause

Cloud Supabase has the reported failed run:

- `run_id`: `run_8290101e249b`
- `worker_id`: `granola-hubspot-meeting-sync`
- `workspace_id`: `ws_b79e570aad8349`
- status: `failed`
- duration: `4436ms`
- error: `Server disconnected`

The run appears in activity lists when the active workspace header is present. Exact run detail used the same active-workspace repository scope as lists, so a stale/default workspace cookie made `runs.get()` miss the owned row and return `Run not found`.

### Fix

Cloud-only repository fix:

- `SupabaseRunRepository.get()` still tries the active workspace first.
- On a miss with an active workspace context, it retries by exact run id plus owner `user_id`.
- The fallback does not expose other users' runs and does not change list scoping.

### Evidence

- `python3 -m pytest tests/test_supabase_repos.py -q` in the Cloud worktree: `4 passed`.
- Patched local Cloud repository probe with active workspace forced to `ws_aac663b43cb542` returned `run_found=True`, `run_id=run_8290101e249b`, and `run_status=failed`.

Live verification will be appended after merge/deploy.
